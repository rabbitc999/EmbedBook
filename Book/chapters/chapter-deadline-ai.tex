\chapter{如何应对紧急的交期} \label{ch:deadline-ai}

前面各章讨论的都是“如何把代码写好”：状态机、任务调度、串口协议、菜单系统……这些知识解决的是“会不会做”的问题。但当项目真正进入倒计时，交期只剩一周甚至一个晚上时，真正决定成败的往往是另一类能力：如何调度自己的时间、如何调度别人的时间、如何调度 AI 这个“新员工”。本章不介绍具体代码，而是结合作者在第~\ref{ch:about-author}~章里讲述的真实经历，讨论校园和职场两种场景下的紧急交期处理。本章的核心观点只有三条：
\begin{enumerate}
\item AI 是廉价的“体力劳工”，不是免费的“脑力军师”，决策权永远不能交给它；
\item 越是时间不够，越要用确定性工具，避开看不懂的“魔法”和养不活的“轮子”；
\item 无论是同学、老师还是老板，谈判的本质都是把“必须交付什么”说清楚，而不是比拼谁的代码写得快。
\end{enumerate}

\section{使用 AI Agent 高效编程}

AI Agent 和普通聊天 AI 最大的区别是：它不止“回答你”，还会真的打开你的工程、读代码、改文件、运行命令。对嵌入式开发来说，这就相当于多了一个不知疲倦、手速极快、但偶尔会自作聪明的实习生。用得好，它是交期压力下最强的外援；用不好，它会把一个能跑的项目改成一个“看起来能跑”的项目。

% ---------------------------------------------------------------------
\subsection{DeepSeek Codex 的部署原则}

Codex 是 OpenAI 推出的 AI Agent 编程平台，它的工作方式不是“你在网页上问一句，它贴一段代码”，而是把整个项目目录当作工作区：先读懂工程结构和现有代码，再按任务修改文件、运行构建命令，最后把改动结果交回给你确认。

作者的习惯是：把 AI Agent 当成“自动代码补全器 + 体力劳工”。生成格式化代码、填充注释、写测试桩、批量重构这类重复劳动可以放心交给它；但“用什么方案、砍哪个功能、代码要不要保留”这类决定，永远自己拍板。就像第~\ref{ch:about-author}~章说的：Agent 可以替你写尽天下代码，但不能替你按下那枚“锤子”。

% ---------------------------------------------------------------------
\subsection{向 DeepSeek 国产大模型开发平台付费}

没有免费的午餐。Codex 虽然是 OpenAI 推出的 AI Agent 编程平台，但国内无法访问 ChatGPT 的任何平台，因此我们需要向国产大模型开发平台付费购买“AI 体力劳动”。此外，如果读者仍想使用 ChatGPT 原版模型，需要清醒地认识到额外的门槛：国内无法直接访问 OpenAI 服务，必须依赖中转 API（如 fhl、co-yes 等）和 VPN 工具（如 Clash）才能连接。费用方面，ChatGPT 的 API 调用成本接近 DeepSeek 的 10 倍，对于频繁生成代码的场景，Token 费用会迅速累积。更关键的是，此类访问方式存在法律合规风险——使用未经批准的翻墙工具和未备案的境外 AI 服务，在我国现行法律法规下可能面临行政处罚甚至更严重的后果。因此，除非您有明确的合规授权和充足的预算，否则强烈建议放弃 ChatGPT，优先使用 DeepSeek 等国产大模型平台。它们不仅价格实惠、访问稳定，而且完全符合国内监管要求，能让您把精力集中在项目交付本身，而不是折腾网络和支付问题。这里的“付费”可以理解成两笔账：

\begin{enumerate}
\item 给平台的 Token 费：DeepSeek 等国产平台提供与 OpenAI 兼容的 API，注册后充值、拿到密钥，再把 Codex 的模型地址指向该平台即可使用。费用通常按 Token 计费，生成一段代码的开销很小，但比“0 元试用”稳定得多；
\item 给 AI 的“工时费”：作者在第~\ref{ch:about-author}~章提到“公司 Token = 免费算力，往死里用”，本质上是把低认知密度的体力劳动外包给 Token，把自己省下来的时间花在真正需要思考的地方。
\end{enumerate}

值得强调的是：付费买来的是“体力”，不是“决策权”。AI 生成 100 行代码只需要几秒钟，但如果它把架构方向带偏了，后面可能要花 100 个小时来还债。所以每次让 AI 动手前，先把边界说清楚：改哪个文件、遵守什么命名规范、不许动哪些核心逻辑。

\subsection{\texttt{AGENTS.md} 的参考声明}

\texttt{AGENTS.md} 是放置在项目根目录的说明文件，用于向 AI Agent 告知项目的组织方式、编码规范、工作流程和安全边界。它相当于一份“员工手册”，让 AI 在不同会话中保持行为一致，避免因上下文丢失而重复解释基础规则。

在紧急交期下，\texttt{AGENTS.md} 的价值在于节省反复沟通的时间：AI 不会写出风格割裂的代码，切换会话或更换 Agent 时也无需重新灌输约定。更进一步，它还可以设定明确的安全防线，例如限制编译输出目录、规定备份机制、定义测试结果的存放格式，甚至包含止损策略（如连续逻辑测试失败后的回滚流程）。以本仓库的实际 \texttt{AGENTS.md} 为例，它不仅规定了编译输出必须放入 \texttt{./Codex-Debug}、每次会话首次修改前增量备份至 \texttt{./Backup}，还详细定义了测试结果的文件命名规则（\texttt{Result/Python-...} 和 \texttt{Result/C++-...}），以及 \texttt{RED-GREEN} 测试循环的失败判定阶梯和止损触发条件。这些规则不是束缚，而是让 AI 在高强度交付压力下依然有章可循，减少试错成本，避免方向跑偏。

需要注意的是，\texttt{AGENTS.md} 只应记录需要所有会话长期遵守的通用规则；仅对当前任务有效的临时指令，直接写在对话提示词中即可。下面给出一份简化版的参考示例，展示了如何组织这些约定：

\begin{lstlisting}
	# AGENTS.md
	> 本文件用于配置 AI 助手的行为规范。
	
	## 全局约定
	- 注释、配置说明和文档使用中文，语气客观
	- 编译输出统一放入 ./Codex-Debug 目录，避免污染源码树
	
	## 命名与代码风格
	- 函数：模块名_功能名（动宾短语）
	- 结构体/枚举：大驼峰命名，可加 _T 后缀
	- 宏定义：全大写加下划线
	- 每个函数提供文档注释，说明用途、参数和返回值
	- 代码组之间用空行分隔，适当添加组注释
	
	## 测试与结果
	- 测试脚本放于 test_python/ 目录，结果输出至 Result/
	- Python 结果命名：Result/Python-YYYY-M-D-<名称>.output.txt
	- C++ 结果命名：Result/C++-YYYY-M-D-<名称>.res.txt
	
	## 安全约束（示例）
	- 涉及编译、烧录等操作建议由人工执行，AI 可提供命令和日志分析
	- 修改 core/ 等核心目录下的接口前，需先征求用户同意
	- 不得删除未被明确要求删除的文件
\end{lstlisting}

实际项目中的 \texttt{AGENTS.md} 可以根据团队习惯和项目复杂度进一步扩展，但核心目标始终不变：用明确、稳定的规则替代临时口头约定，让 AI 成为可靠且可预期的“编外成员”。

\subsection{有必要写 \texttt{SKILL.md} 吗}

\texttt{SKILL.md} 用来描述“一项可以反复执行的工作流”。如果说 \texttt{AGENTS.md} 是 “员工手册”，那么 \texttt{SKILL.md} 就是“标准作业程序”。

举例来说，如果每次给菜单系统新增一个页面，都要依次完成以下步骤：创建菜单项结构体、注册回调函数、更新菜单栈、在 PC 仿真里验证、再移植到单片机，那么就可以把它写成一个 Skill。之后 AI 接到“新增一个页面”的需求时，就会自动按这个流程执行，而不是每次从零猜测。

判断标准很简单：

\begin{itemize}
\item 这个操作只做一两次，或每次做法都不一样 $\rightarrow$ 不写，直接在对话里说；
\item 这个操作会反复出现，且步骤基本固定 $\rightarrow$ 值得写；
\item 操作涉及硬件下载、编译命令、回归测试等不能出错的环节 $\rightarrow$ 强烈建议写。
\end{itemize}

作者的观点是：AI 既然是“体力劳工”，就更应该给它一份固定的“操作手册”，而不是每次都现场教。写 \texttt{SKILL.md} 表面上多花了半小时，但它能把“每次重复劳动都要人盯着”变成 “一次标准化，之后全部自动”，这正是第~\ref{ch:about-author}~章里“用确定性的劳动对冲不确定性风险”的翻版。下面给出一份简单的 \texttt{SKILL.md} 参考示例：

\begin{lstlisting}
# SKILL.md

## 技能名称
新增菜单页面

## 适用场景
需要给现有菜单系统新增一个功能页面时。

## 操作步骤
1. 在 menu_user.c 中创建菜单项结构体，并注册回调函数
2. 在菜单表中登记新页面，设置跳转入口
3. 在 PC 仿真中验证页面显示与按键逻辑
4. 移植到单片机，确认 LCD 与按键驱动正常
5. 运行回归测试，检查原有菜单页面没有受影响

## 注意事项
- 不要修改菜单核心文件 menu.c / menu.h
- 新增 API 必须补充中文文档注释
- 命名必须遵守 AGENTS.md 中的规范
\end{lstlisting}

\subsection{有必要写 \texttt{MEMORY.md} 吗}

\texttt{MEMORY.md}（有的工具里叫 \texttt{MEMORYS.md}）用于保存跨越多个会话的长期信息，比如作者的个人偏好、常用工具链、曾经踩过的坑。它和 \texttt{AGENTS.md} 的分工是：

\begin{itemize}
\item \texttt{AGENTS.md}：面向“当前仓库”，告诉 AI 这个项目该怎么干活；
\item \texttt{MEMORY.md}：面向“长期记忆”，告诉 AI 这个用户习惯怎么干活。
\end{itemize}

是否有必要写，取决于你使用 AI 的频率：

\begin{enumerate}
\item 只是偶尔用一次 AI 写小程序 $\rightarrow$ 没必要，记忆文件反而会成为过时信息的来源；
\item 每天都在同一个开发环境里使用 AI Agent $\rightarrow$ 建议写，至少记录“中文注释、优先使用确定性工具、编译由人执行”这类稳定的个人偏好；
\item 跨项目使用同一套习惯 $\rightarrow$ 可以把通用偏好放记忆，把项目特有规范放 \texttt{AGENTS.md}。
\end{enumerate}

写 \texttt{MEMORY.md} 时要注意两点：第一，只记录“长期不变”的偏好，不要记录会过期的事实；第二，记忆必须定期清理。作者的原则是：AI 可以记住我的习惯，但不能用一条过时的记忆替我做决定。下面给出一份简单的 \texttt{MEMORY.md} 参考示例：

\begin{lstlisting}
# MEMORY.md

## 用户偏好
- 代码注释、文档说明一律使用中文
- 命名遵守仓库 AGENTS.md 的规范
- 优先使用确定性工具，慎用看不懂的黑盒框架
- AI 负责体力劳动，架构决策由用户完成
- 编译、下载、烧录等动作由用户亲手执行

## 常用技术栈
- 单片机：STM32 系列、STC 系列
- 语言：C / C++ / Python
- 工具：Keil、VS Code、Codex、Git

## 注意事项
- 记忆会过期，遇到冲突时以当前对话和 AGENTS.md 为准
\end{lstlisting}

\subsection{其他 AI 常见术语及其含义}

下面整理交期场景下最常遇到的 AI 术语，方便读者阅读资料和向别人描述需求：

\begin{itemize}
\item Token：大模型计费和输入输出的最小单位，可以粗略理解成“字数”。写代码时把需求说清楚、把无关文件收起来，就是在省 Token；
\item Prompt 与 System Prompt：你给 AI 的指令。系统提示词决定 AI 的“人设”，普通对话决定本次任务内容；
\item 上下文窗口（Context Window）：AI 一次能“记住”的最大内容量。工程太大时不能把整个仓库塞进去，需要靠 \texttt{AGENTS.md}、索引或按目录分段喂；
\item Agent：能自主调用工具、读写文件、执行命令的 AI，而不是只回一句话的聊天机器人；
\item Function Call 与 Tool Use：AI 调用外部函数或工具的能力，例如读文件、执行编译、查串口日志，这是 Agent 能“干活”的基础；
\item MCP（Model Context Protocol）：统一 AI 与外部工具或数据源连接的协议，可以理解成 AI 的“USB 接口”，插上什么工具就能用什么能力；
\item RAG（检索增强生成）：先从资料库检索相关内容，再让 AI 基于检索结果回答，用来缓解“凭记忆瞎编”的问题；
\item 微调（Fine-tuning）：用专门数据进一步训练模型，成本高，普通项目几乎用不到，别把它和“写提示词”混为一谈；
\item 幻觉（Hallucination）：AI 一本正经地编造不存在的 API、寄存器或文件。判断方法只有一个：让它运行给你看；
\item 沙箱（Sandbox）：AI 只能在一个受限环境里执行命令，防止误删文件或破坏系统，是保护项目安全的重要机制。
\end{itemize}

面对这些术语，作者的建议始终是：术语只是工具的名字，重点是“谁能替我干活、谁能替我决定”。能看透底牌的工具就多用，看不透的“魔法”就少碰。


\section{打通物理世界与虚拟世界的桥梁}

嵌入式开发和纯软件开发的本质区别，是它同时存在于两个世界：

\begin{itemize}
	\item 虚拟世界：源码、编译器、仿真器、串口日志，Agent可以自由进出；
	\item 物理世界：单片机引脚、电平、示波器波形、电机转动、屏幕刷新。
\end{itemize}

过去作者认为 Agent 永远只能“听说”物理世界，不能“看见”——但那是建立在“使用 Keil 这类封闭式 IDE”的前提下的。要讲清楚为什么必须换工具，得先承认一个令人遗憾的现实。

\subsection{为什么要切换到 OpenOCD + GCC}

说完了 Keil 的遗憾，再来看解决方案就顺理成章了。Keil 的编辑器、调试器与 Codex 之间缺少稳定的命令行接口，AI 无法自动调用编译、下载、读取寄存器，更无法把物理现象实时反馈给 Agent。

需要郑重说明的是：Keil 本身并非“垃圾”。它在国内单片机教学和工业开发中拥有深厚的用户基础，配套的芯片支持包、调试驱动、以及大量现成工程模板都是其优势，很多老工程师和学校实验室早已形成工作习惯。我们批评的只是“用 Keil 的低级编辑器配合 AI Agent 做自动化编程”——因为它的封闭命令行接口和专有编译链确实构成了障碍，而不是否定它作为一款成熟 IDE 的价值。如果您的项目完全由人手工调试、不依赖 AI 自动化，Keil 仍然是一个可靠的选择。

但如果您希望让 AI Agent 真正参与物理世界的调试，就必须抛弃 Keil 的图形界面操作，改用 OpenOCD + ARM-GCC 工具链。OpenOCD（Open On-Chip Debugger）提供了一套完整的命令行调试接口，配合 ARM-GCC 编译链，可以让 AI Agent 通过脚本执行以下操作：

\begin{enumerate}
	\item 编译工程：执行 \texttt{make} 或 \texttt{cmake --build}，捕获编译输出；
	\item 烧录固件：通过 OpenOCD 的 \texttt{flash write\_image} 命令将 \texttt{.bin} 或 \texttt{.hex} 写入单片机；
	\item 读取内存和寄存器：使用 \texttt{mdw}、\texttt{reg} 等命令获取物理状态；
	\item 捕获串口日志：将串口重定向到文件或管道，AI 可实时读取并分析。
\end{enumerate}

这样一来，Agent 不再“听说”物理世界，而是通过命令行管道“看见”它——编译报错、烧录失败、寄存器值异常、串口输出乱码，所有这些现象都能以文本形式被 AI 获取，并据此做出下一步调整。作者在实践中已经验证：配置好 OpenOCD 脚本和 GCC 工具链后，AI 可以自动完成“修改代码 → 编译 → 烧录 → 读取串口日志 → 分析错误 → 再次修改”的闭环，每次迭代只需几十秒，极大压缩了调试周期。

但需要清醒地认识到：即便是 OpenOCD + GDB 的组合，也存在着物理世界的边界。GDB 调试器通过调试接口只能读出数字化的寄存器值和内存数据，它无法直接测量单片机引脚的电压、电流、波形畸变等模拟量——这些信息仍然需要示波器、逻辑分析仪或万用表来获取。也就是说，AI 目前能在“数字域”内自由工作，但对“模拟域”依然只能通过人的转述来间接了解。作者相信，随着 AI 辅助调试工具的发展，未来可能会出现能自动识别波形、解读物理信号的“AI 调试器”，但在那之前，物理世界的异常（例如电平不稳、电源纹波、驱动能力不足）仍需要开发者亲自动手测量，并把测量结果“翻译”给 AI。

无论工具链如何进步，有一条底线始终不能动摇：代码的主动权必须留在开发者手中。AI 可以帮你编译、烧录、读取日志、甚至提出修改建议，但最终的架构决策、功能取舍、以及“这段代码到底要不要合入主分支”这类判断，必须由人来拍板。本章开头就强调过，AI 是“体力劳工”而非“脑力军师”，这条原则在打通物理世界后依然适用——甚至更加重要，因为一旦 AI 能直接操作调试器，它犯错的代价会从“虚拟世界”蔓延到“物理世界”（比如烧坏 Flash 或误设时钟），所以必须通过 \texttt{AGENTS.md} 和人工审查来严格限定其行为边界。

当然，工具链的切换需要一次性投入：安装 ARM-GCC、配置 OpenOCD 的配置文件（目标芯片、调试接口、速度等）、编写简单的 Makefile 或 CMakeLists。但这些工作完成后，AI 就可以在虚拟和物理世界之间自由穿梭，而不用再靠人工抄写日志、手动点击“下载”按钮。

作者仍建议保留最后一道人工防线：涉及擦除 Bootloader、修改时钟配置、写入保护位等高风险操作，应设置为禁止 AI 执行（可在 \texttt{AGENTS.md} 中明确声明）；而普通的编译、烧录、读取寄存器，则完全可以交给 AI 自动化。让 AI 通过确定性的命令行工具接触物理世界，而不是让它操作一个封闭的图形界面——因为命令行可以被脚本化、被审计、被限制，而 Keil 的鼠标操作不能。

最后，如果您的团队暂时无法从 Keil 迁移，那么本章之前“Agent 只能听说”的观点依然成立——因为 Keil 没有为 AI 留出可靠的命令行接口，AI 的参与度会大打折扣。但在新项目或允许技术选型的场景下，强烈建议拥抱 OpenOCD + GCC，这不仅是给 AI 铺路，也是为持续集成、自动化测试和跨平台开发打下基础。

\subsection{Keil 的遗憾与妥协}

前面花了很长篇幅讨论“为什么推荐 OpenOCD + GCC”，也郑重声明了“Keil 并非垃圾”。但说完这些道理之后，我必须面对一个更诚实的问题：你在真实项目中，真的能摆脱 Keil 吗？

答案对绝大多数国内工程师来说是：不能。

这不是技术问题，而是生态问题。STM32 的官方例程、国产 MCU 厂商提供的 SDK、大学实验室里代代相传的工程模板，几乎都默认是 Keil 的 \texttt{.uvprojx} 项目文件。你拿到的电机驱动库、无线模块移植代码、甚至一个简单的按键扫描例程，打开就是 Keil 工程。如果硬要改成 GCC + Makefile，工作量可能比写业务代码还大——而且你还得自己处理启动文件、链接脚本、分散加载、以及那些只有 Keil 才认识的内置宏（如 \texttt{\_\_CC\_ARM}）。

更现实的是，很多国产 MCU 的调试接口只支持 MDK 的调试器（如 DAP-Link 的 CMSIS-DAP 在 OpenOCD 下总有些奇怪的兼容性问题），或者芯片原厂的烧录算法只以 Keil 插件形式提供。这时候鼓吹“抛弃 Keil”就是不负责任的理想主义。

所以我的真实态度是：对 Keil 有深深的遗憾，但不得不与之共处。

遗憾在哪里？

第一，Keil 的编辑器是“上古”级别的。自动补全迟钝、代码跳转不准、重构功能几乎为零。虽然你可以外挂 VS Code 写代码，但编译、下载、调试又必须切回 Keil——这种割裂感在需要频繁“改一版 → 烧录 → 测试”的调试周期里非常消耗精力。

第二，Keil 没有可靠的命令行接口。\texttt{UV4.exe} 可以带参数启动并执行 \texttt{build}，但它无法在构建过程中注入自定义脚本，也无法捕获编译输出的结构化信息（比如错误列表、警告计数）。你无法像用 GCC 那样轻松地把编译过程嵌入 CI/CD 流水线，更不可能让 AI Agent 通过标准输入输出与 Keil 交互。这是它与 Codex 之间存在“鸿沟”的根本原因——不是它不好，而是它没打算让机器来操作它。

第三，Keil 的调试器虽然好用，但它是“人手专用”的。你手动设断点、看变量、修改内存，这些操作 GUI 做得很好，但 AI 无法模拟鼠标点击和窗口观察。即使你用 \texttt{–command} 脚本加载了一些调试指令，也无法像 GDB 那样用文本流实时读取寄存器和内存。也就是说，AI 在 Keil 世界里永远是“眼盲”的——它只能看你的串口打印，却无法直接读取物理世界的状态。

面对这些遗憾，我在实践中采取的妥协方案是“两条腿走路”：

\begin{itemize}
	\item 如果项目是全新启动、芯片支持良好的 GCC 工具链（比如 STM32 全系列、ESP32、RISC-V 等），我会优先建立一套 \texttt{Makefile + OpenOCD + ARM-GCC} 的工程，把 Keil 只作为“备胎”用来比对调试结果；
	\item 如果项目必须沿用已有的 Keil 工程（尤其是国产 MCU 或老项目），我不会强行迁移，而是做两层隔离：业务逻辑全部写在 \texttt{.c} 和 \texttt{.h} 中，保持与编译器无关；Keil 工程只负责启动代码和硬件初始化，并把串口打印作为唯一的信息通道。AI 仍然可以通过分析串口日志来辅助调试，虽然效率不如 OpenOCD 直接读寄存器，但至少能让 AI 发挥一点“远程协助”的作用；
	\item 我还会在 \texttt{AGENTS.md} 中明确告诉 AI：“当前项目使用 Keil，编译和下载由人工执行，你只需提供代码修改建议，不要尝试运行任何命令行”。这虽然限制了 AI 的能力，但也避免了它误操作导致工程损坏。
\end{itemize}

最后，我想说一个也许不太现实但真诚的期望：希望国内的 IDE 厂商（如 RT-Thread Studio、华为的 HarmonyOS IDE 等）或者 Keil 自身，能在未来提供一种稳定的、可脚本化的命令行接口，让 AI Agent 能够像操作 GCC 那样操作编译和调试过程。到那时候，嵌入式开发的“虚拟世界”和“物理世界”才能被真正打通——而今天的这些遗憾，就当作是这个行业转型期的阵痛吧。

至少在今天，我依然会在某些深夜项目里打开 Keil，点一下“Download”按钮，等它烧录完成，再切到串口助手看日志。我知道这不完美，但我知道为什么只能这么做，也接受这种不完美。这种清醒的妥协，或许比盲目的激进更接近工程现实。

\section{校园的紧急交期处理}

校园项目的交期通常来自课程设计、竞赛和毕业设计。它的特点是：时间短、组员水平参差不齐、硬件资源有限，而且很多时候“通过”的标准并不高——但没人告诉你标准到底是什么。

% ---------------------------------------------------------------------
\subsection{同学间的小组分工分配方法}

小组分工最常见的错误，是把任务按“代码量”平均分配：你写一半，我写一半。结果接口对不上、风格不统一、最后两天全组都在联调。

正确的思路是按“接口”和“风险”分工：

\begin{enumerate}
\item 先定接口，再分任务：例如菜单项目先约定好“菜单项结构体长什么样、按键事件怎么传递、界面刷新由谁调用”，之后各组员在自己的模块里互不干扰；
\item 让最靠谱的人负责关键路径：主循环、状态机、通信协议这类“别人都要依赖”的模块，不能交给进度最慢的人；
\item 每个组员都要有可演示的成果：避免一个人埋头写框架、其他人无事可做，最后验收时才发现框架方向错了；
\item 每天合并一次代码：哪怕功能不完整，也要让代码能编译、能跑，防止最后一天才发生“地狱合并”。
\end{enumerate}

在 AI 时代，还可以给每个组员配一个“AI 帮手”，但必须统一规则：用什么模型、遵守什么命名规范、改动哪些文件要提前声明。否则五个人各自让 AI 改五份代码，最后拼起来比手写还慢。

% ---------------------------------------------------------------------
\subsection{如何与实验室老师谈判}

很多同学不敢找老师谈延期，怕被批评；或者只会说“老师，我做不完了”。这两种方式都拿不到资源。老师真正想知道的不是“你有多惨”，而是“你还能交付什么”。

与老师谈判时建议按下面三步走：

\begin{enumerate}
\item 带着进度去，而不是带着困难去：把已经完成的功能现场演示一遍，哪怕只是一个能亮灯、能收发串口的半成品；
\item 给出二选一的具体方案：例如“方案 A：保留基础功能，砍掉数据存储，三天后可交付；方案 B：全部功能保留，但需要再给我一周调硬件”，让老师做选择题，而不是做判断题；
\item 把“完不成”的原因说成风险，而不是借口：硬件采购延迟、某个芯片手册与实物不符，这些是可验证的事实；说“太难了”则容易被理解为态度问题。
\end{enumerate}

记住：实验室老师的核心诉求通常是“这个项目能作为教学案例顺利收尾”，而不是为难你。只要你能证明自己在推进、并且给出一条可行的收尾路径，大部分老师愿意在范围或时间上让步。

% ---------------------------------------------------------------------
\subsection{为什么校园里一定要学会造“塑料轮子”}

这里举作者自己的例子。做毕业设计时，作者一开始认准了 ROS2，觉得它才是“正规轮子”，于是硬啃了三个月：安装环境、学习节点通信、调 EKF 参数……越到后期越焦虑，因为交期一天天逼近，而 ROS2 的工程量根本不是毕业设计剩下的时间能消化的。直到 DDL 真的压到面前，作者才决定先不学 ROS2，改造一个“塑料轮子”：硬件上用双核异构架构，STM32H743 负责运动控制与数据融合，K230 负责视觉识别；软件上放弃 Linux 和 ROS2，用 AI 生成的表达式解析器处理可配置逻辑，再把 EKF 换成基于动态打滑度检测的自适应里程计融合算法，两块芯片之间只靠一条高速串口通信。这套方案谈不上工程美感，但它只花了一周左右就跑通了，最后顺利交付。

为什么校园里一定要学会造塑料轮子？原因主要有几点：

\begin{enumerate}
\item 校园项目的 DDL 通常不可商量：课程设计、毕业设计、竞赛都有硬性截止日期，错过就只能等下一轮。先保证“能交付”，才有资格谈“做得好”；
\item 校园阶段没有“试错预算”：没有成熟的团队、售后和技术社区替你兜底，时间耗在框架学习上，往往意味着论文和答辩一起被拖垮；
\item 校园验收看的是“完整可演示”：老师评审的是功能能不能跑、思路能不能讲清楚，不是架构能不能支撑十年迭代。一个能跑通的塑料轮子，比一个永远学不完的正规框架更有价值；
\item 造塑料轮子本身就是学习：为了绕开 ROS2，你需要自己设计通信协议、写解析器、做传感器融合。这个过程逼你把“黑盒”拆开，反而比直接调用框架更接近底层原理。
\end{enumerate}

需要强调的是：造塑料轮子不等于拒绝学习 ROS2。作者后来再接触 ROS2 时发现，AI Agent 可以帮忙分析日志、批量调节参数，效率比当年手工死磕高得多。也就是说，塑料轮子是校园阶段保护自己的应急技能，不是拒绝成长的借口；等时间、工具都齐备了，再回头把塑料轮子换成正式轮子也不迟。

\section{职场的紧急交期处理}

职场的交期和校园最大的不同，是它背后连着钱、合同和信任。一次延期可能影响整个项目排期，所以处理紧急交期不能只靠加班，更要靠“分析、取舍、谈判”。

% ---------------------------------------------------------------------
\subsection{分析哪些任务必须完成}

时间不够时，第一件事不是埋头写代码，而是先回答一个问题：如果明天就要交付，哪些事情不做就一定会失败？

判断标准可以从“验收视角”倒推：

\begin{itemize}
\item 老板或客户验收时会操作哪些功能？这些功能里的主流程就是必须完成的；
\item 哪些 Bug 会导致死机、数据丢失、无法通信？这些是致命缺陷，必须修；
\item 哪些只是“颜色不对、按钮位置不好看、代码可以更优雅”？这些属于优化，可以放在交期之后；
\item 哪些任务是别人提的“顺手做一下”，不在验收清单里？这类任务要敢于砍掉或明确推迟。
\end{itemize}

分析完之后，把任务分成“必须做”“应该做”“可以不做”三档，然后只承诺第一档的完成时间。需要特别提醒的是：砍任务之前一定要先和相关方说清楚，不能自己默默不做，否则交付时会被认为“漏功能”，而不是“主动取舍”。

% ---------------------------------------------------------------------
\subsection{使用别人的轮子还是自研轮子}

交期压力下，很多人第一反应是“找个现成库赶紧用”。但作者的经验是：轮子不是拿来就能跑的，选错轮子比没有轮子更危险。

如果这个轮子是业余爱好者维护的，或是靠程序员“用爱发电”开发的，即使是 MIT 协议，也要尽可能避免使用。原因很简单：用爱发电的项目，除了一些自律性很高的团体能够长期维护，大多数会随着维护者毕业、换工作、失去兴趣而停止更新。而你的产品一旦依赖它，就等于把交期押在了一个随时可能消失的人身上。

判断一个轮子能不能用，可以看两个日期：该项目的更新日期和目标框架的更新日期。如果两者相差很远，说明这个项目很可能已经跟不上框架的 API 变化，强行接入会出现大量“接口对接不上”的问题。此时迁移 API 的时间成本，往往不如自己写一个。

什么情况下应该自研？

\begin{itemize}
\item 需求非常简单，只有几十行，引入库反而要学它的封装；
\item 现有轮子的 API 与目标框架严重脱节，迁移成本高于重写成本；
\item 这个模块是产品的核心，未来要长期维护、深度定制，不能依赖一个黑盒；
\item 时间紧到没空读源码，但又必须保证每一行都可控。
\end{itemize}

这和第~\ref{ch:about-author}~章里“自研 Qt 绘图层替代 HelixScreen”是同一个逻辑：与其在看不透的封装层里反复试错，不如花一两天梳理需求，用确定的代码换取后面无数个不眠夜的安宁。

% ---------------------------------------------------------------------
\subsection{优化任务强度}

交期越紧，人越容易陷入“用战术上的勤奋掩盖战略上的懒惰”：笔记抄了一大堆、代码写了一大堆、Bug 也修了一大堆，但真正推动项目前进的只有那么几件事。

作者观察到一个现象：学霸学习时往往没有记录很多笔记，他们学习好的原因是会减少自己的记忆量，增加自己的思考时间。编程也一样——高手不是记得更多 API，而是知道哪些东西不必记。

优化任务强度可以从三个方向入手：

\begin{enumerate}
\item 减少记忆量：把命名规范写进 \texttt{AGENTS.md}、把常用操作写进 \texttt{SKILL.md}、把重复命令做成脚本，让 AI 和工具替你记；
\item 增加思考量：把省下来的时间用来想“这个功能真的需要吗”“这个方案三个月后还能改吗”，而不是用来背 API；
\item 降低切换成本：一次只专注一个模块，避免在菜单、通信、算法之间来回跳转，因为人的大脑切换上下文比编译器慢得多。
\end{enumerate}

用作者的话说：物理上的勤快要用来换取认知上的偷懒，而不是反过来。

% ---------------------------------------------------------------------
\subsection{明确责任边界}

“甩锅技巧”这个说法听起来略显负面，但作者在此想表达的其实是另一层含义：紧急交期之下，最令人头疼的往往不是任务繁重，而是责任边界模糊不清——一旦出现问题，各方互相推诿，最终所有人都在修改代码，却没有人真正把问题修正。

作者在第一家公司任职时，团队采用流水线式的 WBS 规划，每位成员只负责自身的一小块模块。作者很快察觉到，产品中的 UI 模态框种类繁多，每一种外观相似却各自独立实现，每当需求变更，就必须逐一修改所有模态框。于是作者找到设计师同事，提议将所有模态框统一为一个公共组件。

这一提议的巧妙之处在于：它并非在“转移责任”，而是在从根源上“消除责任争议”。

\begin{itemize}
	\item 模态框统一之后，需求变更只需修改一个公共组件；
	\item 所有同事的改动都基于同一套接口，联调时不会再出现“我这边没有问题，是他那边格式不对”之类的争执；
	\item 出现问题时，可通过日志快速定位到具体模块，而无需在十几个相似实现中人工排查。
\end{itemize}

因此，真正有效的“防甩锅策略”可以归纳为：

\begin{enumerate}
	\item 将接口定义清楚：明确谁负责输入、谁负责输出、异常由谁处理，并以书面形式固定下来；
	\item 收敛重复内容：将多种模态框合并为一种、多种消息格式统一为一种，公共部分越少，潜在的争议点就越少；
	\item 让 Bug 可定位：为每个模块配置独立的日志前缀和错误码，遇到问题时先查看日志再开会讨论，而非先开会互相指责；
	\item 重要决策留痕：在邮件、会议纪要、代码注释中写明“为何如此设计”，日后有争议时可依据事实进行判断。
\end{enumerate}

\subsection{职场里也有“塑料轮子”}

有趣的是，造塑料轮子并不是校园专属。作者后来在工作时发现，组长也会造塑料轮子。当时项目组在调试一台3D打印机，屏幕需要实现“定时息屏”功能，但硬件电路设计有缺陷——背光控制引脚的电压输出不准，无法干净地关断背光，强行拉低会导致屏幕闪烁，甚至影响主控稳定性。硬件同事表示重新打板要等两周，而产品下周就要参展。

组长评估后给出了两种软件方案：方案A是用PWM调光把背光亮度逐渐降到最低，模拟“息屏”效果；方案B是在到达设定时间后，直接把显存里的全部内容绘制成纯黑，背光保持原亮度不变。表面上看PWM调光更“正规”，但组长最终选了方案B——原因很简单：这块屏幕如果长时间完全关闭背光，液晶层会因为电压偏置异常而逐渐泛白，重新点亮时要等好几秒才能恢复正常显示。而PWM调光在低亮度区间会放大硬件电压不准的问题，导致屏闪，反而更难看。全黑缓冲区虽然“骗”了用户的眼睛，但背光一直亮着，屏幕不会泛白，下次唤醒时也能立即响应。

更值得注意的是，组长写完这个功能后，特意把它封装成了宏定义：

\begin{lstlisting}[language=C]
#define SCREEN_BLANK_ENABLE    1
#define SCREEN_BLANK_TIMEOUT   300   /* 单位：秒 */
#define SCREEN_BLANK_FILL_COLOR 0x0000  /* RGB565 纯黑 */
\end{lstlisting}
他的理由是：这个方案只是“当前硬件版本”的临时对策，等硬件改版后肯定要换掉。把息屏开关、超时时间、填充颜色全部抽成宏，将来硬件改版时，直接关掉 \texttt{SCREEN\_BLANK\_ENABLE} 宏就能切回正常背光控制，不用在代码里到处找、到处改。整个实现只用了不到一百行代码，一个下午就搞定，但可读性和可回滚性一点没打折。

组长后来笑着说：“硬件解决不了的问题，就用软件骗过去——只要用户看不出来，它就是对的。但你要搞清楚，骗的是用户的眼睛，不是骗自己——我知道背光没关，也知道为什么要让它亮着。而且改版之后，这一百行代码我一行都不用改，关个宏就切走了。”

这件事让作者意识到：塑料轮子不是能力不足的妥协，而是资源受限时的生存智慧。 选全黑缓冲区不是为了偷懒，而是在两个都不完美的方案里，选了一个刚好避开硬件缺陷、同时满足交期的答案。而用宏定义包装临时方案，说明真正的老手即使造塑料轮子，也会把“将来换掉它”的路提前铺好——这就是第~\ref{ch:about-author}~章里反复强调的“用确定性的劳动对冲不确定性的风险”。校园阶段学会造塑料轮子，不是为了拒绝正规方案，而是为了在将来面对真正的工程约束时，能像组长一样——看清每个方案的代价，然后在有限条件下做出最不坏的选择，同时为下一次改版留好后路。

\subsection{如何与老板谈判}

程序员普遍不擅长谈判，不是嘴笨，而是总想用技术细节说服对方。老板不关心你用了什么设计模式，他只关心：什么时候能交付、要花多少钱、风险是什么。

作者遇到过这样一件事：设计师同事认为，要统一 UI 模态框就得找老板谈判，因为改动范围跨越多个模块。作者的建议是：直接去找老板，把核心需求说出来就好。

具体怎么说？

\begin{enumerate}
	\item 先讲现状：现在系统里有十几种模态框，视觉不统一，每次加新功能都要重复开发；
	\item 再讲方案：统一成一个公共组件，以后新增弹窗只需填参数；
	\item 最后讲代价：需要两天重构时间，但之后每次改 UI 都能节省大量工时，长期收益远大于短期成本；
	\item 给老板一个明确的问题：“是否同意用两天时间做这次统一？”
\end{enumerate}

因为程序员没几个说话利索的，这个时候最重要的不是展示口才，而是表述明确：把“我要什么、为什么、花多久、风险是什么”一次说清。老板最怕的不是你提要求，而是你提了一个他听不懂的要求。

谈判时还要守住一条底线：承诺过的交期一定要兑现，或者提前暴露风险。宁可一开始说“这个功能需要三天”，也不要最后说“其实昨天就该告诉你做不完”。信任一旦透支，下一次再紧急的交期，就没有人愿意听你谈判了。

\section{软件哲学：能跑、正确、优化的三段式辩证法}
本章通篇讨论的“交期策略”，如果抽离出具体的工具和场景，其实指向一条贯穿所有软件开发活动的底层哲学——先能跑，后正确，最后优化。这三者不是线性的时间顺序，而是一套需要根据语境反复切换的决策框架。

\subsection{能跑，是对“存在性”的赌注（Make it Work）}
在交期压顶、资源未知、需求模糊的初始阶段，唯一的目标是让系统“活过来”。此时硬编码、全局变量、阻塞延时都是可接受的——因为它们确定且短视，能最快地验证“这条路是否走得通”。作者在毕设中放弃ROS2改用裸机串口、组长用全黑缓冲区替代PWM调光，本质上都是在“能跑”阶段做出了最不坏的抉择。这个阶段最忌讳的，是用“未来可维护性”绑架当下的交付——没有跑起来的代码，根本不配谈架构。

\subsection{正确，是对“确定性”的承诺（Make it Right）}
当系统能跑之后，必须尽快进入“正确”阶段：消除随机故障、明确边界行为、建立可复现的逻辑。按键消抖、FIFO防丢包、HardFault捕获，这些看似“锦上添花”的工作，实则是把程序从“碰运气”升级为“有契约”。但必须清醒地认识到：正确性只对当前需求负责，不必过度设计。如果产品生命周期只有一次演示，那么“能跑”阶段的硬编码可能就是它的终极形态——正确性的边界由项目的真实寿命决定，而非由工程师的完美主义决定。

\subsection{优化，是对“长期性”的敬意（Make it Fast）}
只有在“正确”已经稳固、且项目确实需要长期维护或迭代时，才应该投入资源进行优化——无论是时间上的（DMA、查表法）、空间上的（内存池、参数迁移），还是结构上的（接口抽象、代码生成）。但优化的前提是必须留有回滚路径：组长用宏封装息屏方案、作者用simple\_task替换FreeRTOS时保留裸机兼容层，都是为了让“优化”本身可逆。如果优化让代码变得难以理解或难以回退，那它就不是优化，而是另一种形式的“炫技债务”。

\subsection{三段式循环的终极启示}
“能跑、正确、优化”并非单向的阶梯，而是一个以项目生命周期为轴的螺旋。每一次需求变更、每一次硬件改版、每一次交期迫近，都可能让你重新回到“能跑”阶段。真正成熟的工程师，不是永远停留在某一阶段，而是能根据当前语境，迅速判断自己应该处于哪个阶段，并且敢于在该阶段全力以赴、在下一阶段果断重构。这正是“塑料轮子哲学”的内核——在荒野中，用铁丝求生；在工厂里，用标准件迭代；但始终记得，工具只是语境的孩子，决策才是工程师的尊严。

正所谓Kent Beck所说的那样：“Make it work, make it right, make it fast” 。

\section{总结本章}
面对紧急交期，AI 负责提高“体力上限”，自研还是用轮子决定“风险下限”，而谈判能力决定“交付底线”。三者合在一起，就是作者在第~\ref{ch:about-author}~章里反复强调的那句话——活着通关才是硬道理。
