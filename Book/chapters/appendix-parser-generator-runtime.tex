\section{文法文件的输入格式}

\texttt{parser.py} 接收一种精简的 Yacc 风格文法。\texttt{STRING}、\texttt{NUMBER} 和 \texttt{VARIABLE} 默认存在；固定字符串 Token 通过 \texttt{\%define} 声明，起始非终结符通过 \texttt{\%start} 声明，动态变量通过 \texttt{\%var} 声明，每条产生式独立写成一行。

\begin{lstlisting}
/* 声明固定字符串 Token，竖线只表示候选“或” */
%define PLUS "+"
%define STAR "*"
%define LPAREN "("
%define RPAREN ")"
%start expr

/* 声明一个由生成器初始化的动态变量 */
%var total int32 = 0

/* 每条产生式包含左部、右部和语义动作 */
expr := expr PLUS term { $$ = $1 + $3; }
expr := term           { $$ = $1; }
term := term STAR atom { $$ = $1 * $3; }
term := atom           { $$ = $1; }
atom := NUMBER         { $$ = $1; }
atom := LPAREN expr RPAREN { $$ = $2; }
\end{lstlisting}

这里的 \texttt{\$\$} 表示当前产生式的结果，\texttt{\$1}、\texttt{\$2} 和 \texttt{\$3} 表示右部各符号的语义值。它们不是 Python 变量，也不是 C 宏，而是生成器在语义动作转换阶段识别的占位符。

\subsection{词法切分}

类 \texttt{\_GramTokenizer} 逐字符扫描文法文本。它先处理空白和注释，再用正则表达式识别数字、字符串、标识符、美元占位符、运算符和换行。换行没有被完全丢弃，因为 \texttt{\%token} 与 \texttt{\%start} 指令需要用行尾判断结束位置。

扫描器需要特别处理三种容易出错的边界：

\begin{enumerate}
\item 字符串内部的注释符号只是普通字符，不能提前结束扫描；
\item 转义字符需要与后一个字符一起读取，避免把转义引号误判为字符串结尾；
\item 语义动作中的花括号可以跨行，必须按配对深度寻找真正的结束位置。
\end{enumerate}

发现无法识别的字符时，加载器抛出 \texttt{GrammarLoadError}，并保留字符位置。错误在生成期暴露，比生成一个不完整的 C 文件以后再交给编译器处理更容易定位。

\subsection{运行期默认 Lexer}

生成的 Lexer 默认提供 \texttt{STRING}、\texttt{NUMBER} 和 \texttt{VARIABLE}。数字根据形式创建动态值：普通整数为 \texttt{int32\_t}，\texttt{u} 后缀为 \texttt{uint32\_t}，小数或科学计数法为 \texttt{float}，浮点形式加 \texttt{d} 后缀为 \texttt{double}。字符串在 Lexer 内完成反转义，变量 Token 保存名称而不提前查表。

\texttt{\%define EQ "==|="} 中的竖线只表示两个固定候选，不是正则表达式。Python 会按长度降序生成规则，所以 \texttt{==} 先于 \texttt{=} 匹配。

\section{First 集、Follow 集与选择集}

生成器要根据当前 Token 选择产生式，因此必须知道一条产生式可能从哪些终结符开始。对符号串 $\alpha$，First 集记为 $\operatorname{FIRST}(\alpha)$；对非终结符 $A$，Follow 集记为 $\operatorname{FOLLOW}(A)$。

如果产生式 $A\rightarrow\alpha$ 不能推出空串，它的选择集为：

\begin{equation}
\operatorname{SELECT}(A\rightarrow\alpha)=\operatorname{FIRST}(\alpha)
\end{equation}

如果 $\alpha$ 可以推出空串 $\varepsilon$，选择集还要包含 $A$ 的 Follow 集：

\begin{equation}
\operatorname{SELECT}(A\rightarrow\alpha)=
\bigl(\operatorname{FIRST}(\alpha)-\{\varepsilon\}\bigr)
\cup\operatorname{FOLLOW}(A)
\end{equation}

\texttt{compute\_first} 和 \texttt{compute\_follow} 都使用“不动点迭代”：反复扫描全部产生式，只要集合仍有新增元素就继续，直到一轮扫描没有变化。文法规模通常很小，这种实现比引入复杂图算法更直接。

同一个非终结符的两条候选产生式如果在同一个 Token 上拥有重叠选择集，生成器会报告“文法不是 LL(1)”。这是一个生成期错误，因为生成的 \texttt{switch} 无法为同一个 \texttt{case} 同时选择两条规则。

每次生成时，工具都会在控制台输出转换后的最终产生式、FIRST、FOLLOW 和预测分析表。参数 \texttt{--report 文件名} 可以保存相同的 UTF-8 报告；发生冲突时，错误会指出具体表项及其对应的两条产生式。

\section{直接左递归与非递归预测分析}

普通 LL(1) 文法不能含有左递归。生成器遇到 $E\rightarrow E+T\mid T$ 时，会在 Python 端先构造合成尾非终结符，再对最终文法计算 FIRST、FOLLOW 和预测表：

\begin{equation}
E\rightarrow T\ E\_tail,\qquad
E\_tail\rightarrow +T\ E\_tail\mid\varepsilon
\end{equation}

转换过程会保留原动作与“上一轮结果”的关系。基产生式动作先得到累计值；续产生式把该值放入原规则的 \texttt{\$1}，计算后再传给下一个尾规则。因此减法和除法仍保持左结合。当前实现只转换直接左递归；间接左递归会在生成阶段报告完整环路。

生成的 C 不为非终结符创建递归函数，而是使用三类显式数据：

\begin{itemize}
\item 预测分析表：根据“非终结符 + 当前 Token”选出产生式；
\item 分析栈：逆序保存待匹配符号与待执行动作；
\item 语义帧栈：保存 \texttt{\$1}、\texttt{\$2}、变量名和产生式结果。
\end{itemize}

\begin{lstlisting}[style=c]
/* 概念性伪代码：实际代码由 parser_gen.py 输出 */
while (context.stackTop > 0u) {
    item = Parser_Pop(&context);
    if (item.kind == PARSER_ITEM_TERMINAL) {
        Parser_MatchTerminal(&context, item);
    } else if (item.kind == PARSER_ITEM_NONTERM) {
        production = table[item.symbol][context.current.type];
        Parser_ExpandProduction(&context, production);
    } else {
        Parser_ExecuteAction(&context, item.symbol);
    }
}
\end{lstlisting}

这里的“非递归”指语法分析不再随文法嵌套增加 C 调用栈。最大深度由 \texttt{PARSER\_MAX\_STACK\_DEPTH} 明确控制，超过容量时返回错误，避免在小栈 MCU 上悄悄触发 HardFault。
\section{语义动作转换器}

文法右侧花括号中的内容不是直接复制到 C 文件。类 \texttt{\_ActionTranslator} 会再次对动作文本做词法分析，并用 Pratt 解析方法处理运算符优先级。这样，\texttt{\$1 + \$3 * \$5} 能够先生成乘法，再生成加法。

内部表达式节点 \texttt{\_ExprNode} 区分两类值：

\begin{itemize}
\item \texttt{raw}：普通 C 标量，携带 \texttt{int32}、\texttt{float} 或其他静态类型；
\item \texttt{ptr}：指向 \texttt{VarValue\_T} 的运行时值，具体类型要到运行时读取。
\end{itemize}

这一区分决定运算符如何生成，如表~\ref{tab:app-action-map}~所示。

\begin{table}[htbp]
\centering
\caption{语义动作的主要转换规则} \label{tab:app-action-map}
\begin{tabularx}{\textwidth}{llX}
\toprule
动作写法 & 生成形式 & 说明 \\
\midrule
\texttt{\$\$ = \$1 + \$3;} & \texttt{Var\_Add(...)} & 两侧为运行时对象时调用动态运算 \\
\texttt{\$\$ = int32(3);} & \texttt{Var\_CreateInt(3)} & 类型构造器创建新对象 \\
\texttt{\$1.float} & \texttt{Var\_ToDouble(...)} & 把运行时值读取为 C 标量 \\
\texttt{[\$1] = \$3;} & \texttt{Parser\_AssignVariable(...)} & 转换后写入已有固定类型变量 \\
\texttt{def[\$1,int32] = \$3;} & \texttt{Parser\_DefineTyped(...)} & 定义并固定变量类型 \\
\texttt{\$1.int32 = 5;} & \texttt{Var\_SetInt(...)} & 覆盖对象内容但保持对象地址不变 \\
\bottomrule
\end{tabularx}
\end{table}

直接给 \texttt{\$1} 赋一个新对象会改变子结果指针，原对象的归属关系随之丢失，因此生成器明确拒绝这种写法。需要修改变量时，应使用带类型字段的赋值；需要产生新的当前结果时，应给 \texttt{\$\$} 赋值。

生成期能够确定的 C 标量遵循一组简化提升规则：相同类型保持不变；只要一侧是 \texttt{double}，结果就是 \texttt{double}；存在其他浮点类型时结果为 \texttt{float}；两个不同整数类型统一提升为 \texttt{int64}。运行时对象之间的算术则交给 \texttt{Var\_Add}、\texttt{Var\_Sub}、\texttt{Var\_Mul} 和 \texttt{Var\_Div}。

位运算和移位没有定义为动态对象操作。遇到运行时对象时，生成器会发出警告并按整数读取。这个选择保证生成过程能够继续，但也提醒文法作者显式写出目标类型，避免依赖隐式截断。

\section{生成的 C 解析器结构}

生成结果主要包含默认 Lexer、Token 枚举、预测分析表、显式分析栈、语义帧栈和变量注册表。\texttt{Parser\_Run} 继续接收调用者准备的 Token 数组；\texttt{Parser\_RunText} 则直接从脚本文本按需取出 Token。

\texttt{parser.py} 还会把 \texttt{variable\_runtime.c/h} 的完整内容复制进同一个输出文件，使生成结果不再依赖仓库里的运行时源码。文件末尾默认附带演示 \texttt{main()}：编译后运行可解析 \texttt{argv[1]}（缺省使用 \texttt{PARSER\_DEMO\_INPUT}），并递归打印数组等结果。需要把生成文件作为库嵌入其他工程时，在 \texttt{\#include} 前定义 \texttt{PARSER\_SKIP\_DEMO\_MAIN} 即可关闭演示入口。

若文法开头包含 \texttt{\%tree}，生成代码还会附带通用语法树 API：\texttt{Parser\_ParseTreeText} 返回根节点，根节点与子节点都是 \texttt{VarValue\_T} 结构体，字段包含 \texttt{name}、\texttt{text} 与 \texttt{children}；外部程序可用 \texttt{Parser\_TreeGetName}、\texttt{Parser\_TreeGetText}、\texttt{Parser\_TreeGetChildren} 遍历，或用 \texttt{Parser\_TreePrint} 直接打印。

预测表单元保存产生式编号。主循环展开产生式时逆序压栈，使符号仍按文法从左到右匹配；动作标记最后执行，并把结果回填父语义帧。整个语法分析过程没有非终结符函数之间的递归调用。

\begin{anybox}{固定的语义值数组}
生成器根据最终文法的最长右部计算每个语义帧的 \texttt{values} 槽位数量；分析栈和语义帧的总深度由 \texttt{PARSER\_MAX\_STACK\_DEPTH} 配置。容量不足会返回明确错误，不会越界写入。
\end{anybox}

\section{创建、深拷贝与递归释放}

动态对象的生命周期可以概括为三条规则：

\begin{enumerate}
\item \texttt{Var\_Create...} 返回的新对象由调用者持有；
\item 对象加入数组、字典或结构体后，容器接管该对象；
\item 最外层对象交给 \texttt{Var\_Free} 后，内部缓冲区和全部子对象递归释放。
\end{enumerate}

\texttt{Var\_CloneValue} 不是复制一个指针，而是深拷贝整棵对象树。字符串会获得新的字符缓冲区，数组元素和字典值会递归克隆。这样，三元表达式和拼接结果不会与原对象共享可释放内存。

\texttt{Var\_SetValue} 也采用深拷贝。它先克隆源对象，再用新内容替换目标对象内部内容，最后释放目标对象原来的内容。目标对象本身的地址保持不变，所以已经保存该地址的变量表不需要更新。

脚本变量定义后类型固定。\texttt{Parser\_AssignVariable} 先调用 \texttt{Var\_ConvertValue} 按目标类型构造完整临时值，转换全部成功后才替换目标内容。浮点转整数截断小数，超出目标范围返回 \texttt{VAR\_RUNTIME\_ERR\_RANGE}；字符串不隐式转换为数值。数组逐元素转换，任一元素失败时原数组保持不变。

外部 C 程序不必直接访问联合体，可以调用 \texttt{Var\_GetInt32}、\texttt{Var\_GetUint32}、\texttt{Var\_GetFloat}、\texttt{Var\_GetDouble} 和其他同族 Getter。这些函数通过输出参数返回结果，失败时不修改输出参数，因此能够区分“值为 0”和“转换失败”。

\section{容器扩容、切片与拼接}

数组、字典和结构体都维护 \texttt{length} 与 \texttt{capacity}。容量不足时，运行时申请更大的存储区并复制旧内容。扩容失败必须保持原对象仍然可释放，不能先丢掉旧指针再检查分配结果。

切片接口 \texttt{Var\_Slice} 同时支持字符串和数组。负数下标会从尾部换算，超出范围的结束位置会被限制到有效长度。字符串切片复制字符区间，数组切片深拷贝元素，因此切片结果可以独立释放。

拼接接口 \texttt{Var\_Concat} 只接受两个字符串，或者两个数组。字符串结果重新分配完整字符缓冲区；数组结果依次克隆左右两侧元素。不同容器类型之间没有隐式拼接，类型不匹配时返回 \texttt{VAR\_RUNTIME\_ERR\_TYPE}。

\section{错误传播与失败边界}

生成器错误和运行期错误需要分开处理：

\begin{table}[htbp]
\centering
\caption{不同阶段的错误及处理方式} \label{tab:app-parser-errors}
\begin{tabularx}{\textwidth}{llX}
\toprule
阶段 & 典型错误 & 处理方式 \\
\midrule
文法加载 & 未知字符、未定义符号、花括号不配对 & 抛出 \texttt{GrammarLoadError} 并停止生成 \\
文法分析 & LL(1) 选择集冲突、只有左递归而没有基产生式 & 抛出 \texttt{ValueError} 并指出规则名称 \\
动作转换 & 左值非法、未知标识符、类型字段错误 & 在生成期拒绝该语义动作 \\

\bottomrule
\end{tabularx}
\end{table}

动态除法还需要调用者特别关注。整数除数为零时 \texttt{Var\_Div} 返回空指针；非整数分支转换为 \texttt{double} 后执行浮点除法，行为遵循目标 C 运行库和浮点环境。语义动作若没有检查空指针，错误可能继续传播到更高层。

\section{与 Param\_T 动态参数的区别}

第~\ref{ch:command-parser}~章的 \texttt{Param\_T} 也带有类型标签，但它和本附录的 \texttt{VarValue\_T} 解决的问题不同。

\begin{table}[htbp]
\centering
\caption{Param\_T 与 VarValue\_T 的职责对比} \label{tab:app-param-var-compare}
\begin{tabularx}{\textwidth}{lllX}
\toprule
对比项 & Param\_T & VarValue\_T & 说明 \\
\midrule
主要用途 & 命令参数识别 & 语言语义值 & 前者重在输入转换，后者重在运行时计算 \\
生命周期 & 通常随命令缓冲区结束 & 需要显式创建和释放 & 动态运行时具有完整所有权模型 \\
容器类型 & 不提供 & 数组、字典和结构体 & \texttt{VarValue\_T} 可以形成对象树 \\
动态运算 & 由适配器读取后计算 & 由 \texttt{Var\_...} 函数计算 & 后者支持运行时类型分派 \\
内存代价 & 较小 & 较大 & 容器和深拷贝都会使用动态内存 \\
\bottomrule
\end{tabularx}
\end{table}

不能因为两者都叫“动态类型”，就让命令参数直接承担脚本运行时职责。\texttt{Param\_T} 适合把一行命令转换成几个标量，\texttt{VarValue\_T} 适合保存会继续参与表达式计算和容器操作的值。

\section{生成命令与验证顺序}

使用文本格式文法时，可以执行：

\begin{lstlisting}[language=Python]
# 中文说明：读取文法文件并生成 C 解析器
python Chapter-script-engine/parser_gen.py \
    --grammar-file Chapter-script-engine/grammar_calc.gram \
    --report parser_calc.report \
    -o parser_calc.c
\end{lstlisting}

生成出的 \texttt{parser\_calc.c} 已内嵌动态类型运行时和演示 \texttt{main()}，不需要再链接 \texttt{variable\_runtime.c}：

\begin{lstlisting}[language=Python]
gcc parser_calc.c -lm -o parser_calc
./parser_calc "(1+2)*3"
\end{lstlisting}

建议按照下面的顺序验证：

\begin{enumerate}
\item 先让加载器读取最小文法，确认指令和产生式能够形成内部模型；
\item 故意加入一个未定义符号，确认生成期能够拒绝错误文法；
\item 故意制造两个选择集冲突的产生式，确认 LL(1) 检查生效；
\item 用整数表达式检查优先级和左结合；
\item 再加入浮点数、字符串和数组，检查动态类型创建与释放；
\item 最后使用内存检查工具反复运行，观察失败分支是否仍能释放临时对象。
\end{enumerate}

\section{单片机使用边界}

Python 生成器适合放在构建电脑上，生成的 C 解析器可以移植到单片机；动态类型运行时是否适合移植，则取决于 RAM、堆管理和实时性要求。

\begin{itemize}
\item 资源紧张的单片机可以只使用生成的语法分派结构，把语义值改为固定结构体；
\item 需要动态容器时，应为 \texttt{malloc} 建立失败策略，并测量最坏内存占用；
\item 实时控制中断不应执行字符串创建、容器扩容和递归释放；
\item 文法、变量表和最大产生式长度应在生成期完成边界检查；
\item 长期运行设备需要对解析失败路径做内存泄漏测试，不能只测试成功表达式。
\end{itemize}

\section{本附录小结}

语法转换器的价值不只是“少写几段 C 代码”，而是把文法合法性、选择集冲突和语义动作类型问题提前到生成期。单文件 \texttt{parser.py} 负责文法加载、分析报告、默认 Lexer、非递归预测分析代码生成，并直接把 \texttt{variable\_runtime.c/h} 内嵌进产物；生成出的 C 文件在运行期自带动态值创建、类型转换和容器管理，还附有演示 \texttt{main()}。生成期和运行期边界清晰以后，解析器才能既方便扩展，又不把文法分析复杂度塞进目标单片机。
